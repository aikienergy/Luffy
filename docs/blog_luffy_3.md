# LUFFY 開発記 #3 — 「魅力的な機能」が乗っていた“間違った土台”と、ブランチ一本化の作法

> 前々回（`docs/blog_luffy.md`）で 6 フェーズの酵素設計ループを、前回（`docs/blog_luffy_2.md`）で「出典付きでも間違っていた」kcat/Km を**全文逐語照合**で確定し直した話を書きました。本記事はその続編です。テーマは 3 つ。
>
> 1. **なぜ開発が二股に分かれていたのか** — 「実機に近い機能」を盛った枝と、「正しい土台」を整えた枝が、別々に育っていた問題。
> 2. **どう一本化したのか** — マージではなく、**検証済みの土台へ機能を Phase 単位で“移植”** した 3 段階。
> 3. **何を捨て、何を残したか** — AI 予測キネティクスの導入と、`Literature > AI-predicted > Estimated` の 3 階層プロビナンス。

---

## 0. これまでのあらすじ

LUFFY はセルラーゼ（EG / CBH / BG）の **AI 逆設計プラットフォーム**です。配列 → 文献アンカー → ESM-2 埋め込み → Tellurium による糖化カスケード → ガウス過程(GP)で収率予測 → 逆設計、という流れでした。

前回（#2）で確定したのは「**全文で確認できない値は採用しない**」という規律です。10 種の文献酵素を `verification_status = full-text confirmed` で固め、α（アクセシビリティ係数）を **3.80**（72 h で転化率 79.1 %）に較正し直しました。`pytest` は 31 passed。

ところが、この #2 の作業が `main` で進む裏で、**もう一本の枝 `feature/real-biomass` が独自に育っていました**。本記事は、その二股をどう畳んだかの記録です。

---

## 1. 「実は」二つのブランチは、別の正しさを持っていた

### 1.1 それぞれが持っていた“良いもの”

| | `main`（#2 の成果） | `feature/real-biomass` |
|:---|:---|:---|
| キネティクス | **全文照合済み 10 種**＋ヒューリスティック | OED/BRENDA 由来＋**DLKcat（AI 予測）** |
| 酵素データ | EG 偏重（100 種, EC 3.2.1.4） | **均衡 141 種**（EG/CBH/BG ＝ 59/50/32） |
| 物理モデル | 3 酵素カスケード＋Φ(X) 減衰、**較正 PASS** | **リグニン阻害＋幾何アクセシビリティ**（実バイオマス） |
| UI | 出典パネル・文献帯・source_badge | **前処理・リグニン・FPU** の実機寄り操作 |
| 土台 | #2 の修正・較正・プロビナンス済み | **#2 より前の枝**から分岐（旧較正・旧 kcat） |

両方に魅力がありました。`main` は**正しい**。`feature` は**面白い**（実バイオマスを扱える）。

### 1.2 “実は”の核心 — 面白い機能は、古い土台の上に乗っていた

`feature/real-biomass` は、共通祖先 `94b15c2`（#1/#2 以前）から分岐していました。つまり、リグニン阻害も AI 予測キネティクスも、**前回暴いた「桁違いに速い BG」や旧較正の上に積まれていた**のです。素朴に `git merge` すれば二択でした。

- **feature を活かす** → #2 の全文照合・再較正が巻き戻る（誤値が復活する）。
- **main を活かす** → せっかくの実バイオマス物理と AI キネティクスが死ぬ。

実際、マージの予行で衝突は 5 ファイル（`app.py` / `validator.py` / `screening.py` / `design_engine.py` / `enzyme_kinetics.csv`）。しかも両者は **API そのものが別物**でした（feature は `run_multienzyme_simulation`、main は `run_cellulolytic_simulation`）。さらに feature には **壊れた `libs/CatPred`・`libs/DLKcat` の git submodule リンク**まで紛れていました。

> 教訓その 1：**衝突の本質はテキストではなく“土台”だった。** 行単位のコンフリクトを解いても、古い較正と新しい較正は同居できません。

---

## 2. どう一本化したか — マージではなく「Phase 単位の移植」

採った方針は単純です。**`feature` を `main` に混ぜない。`feature` の“良いもの”だけを、検証済みの `main` の上へ Phase 単位で移植する。** そして全 Phase を通じて、**較正の参照（金）＝ #2 の全文照合済み 10 種**を動かさない。これが効きました。

### 2.1 Phase 1 — リグニン阻害＋幾何アクセシビリティを“中立デフォルト”で載せる

実バイオマスの肝は、**結晶性・リグニン・前処理**が酵素のセルロース攻撃を阻むことです。これを 2 つの係数として定式化しました。

- **リグニン阻害**（`calculate_inhibition_factor`）：Langmuir 型の非生産的吸着 `α_ads = (L·H)/(k_ads + L·H)` ＋フェノール/フルフラルの非競合阻害。`H` はバイオマス型ごとの疎水性（軟材>硬材>草本）。出典：Li & Zheng (2017), Ximenes et al. (2010)。
- **幾何アクセシビリティ**（`calculate_accessibility`）：`表面項 = 1/(1+(d/d_ref)^1.5)` ×`結晶項 = 1 − CrI·(1 − severity)`。粒径 `d` が小さいほど、前処理 severity が高い（結晶構造を壊す）ほど高い。出典：Alvira et al. (2010)。

この 2 つの積を **`bio_factor`** とし、カスケードの**セルロース攻撃反応（EG・CBH）だけ**に掛けます（BG は可溶性セロビオースに作用するので掛けない）。

```python
# validator.run_cellulolytic_simulation の SBML 内
J_EG:  Cel -> 0.5 C2; kcat_EG  * E_EG  * bio * Phi * Cel/(Km_EG  + Cel) / (1 + C2/Ki_EG);
J_CBH: Cel -> 0.5 C2; kcat_CBH * E_CBH * bio * Phi * Cel/(Km_CBH + Cel) / (1 + C2/Ki_CBH);
J_BG:  C2 -> 2 G;     kcat_BG  * E_BG        * C2/(Km_BG*(1 + G/Ki_BG) + C2);
```

ここが設計上の一番のポイントです。**`bio_factor` のデフォルトは 1.0（中立）**。引数にバイオマス物性を渡さない限り、式は #2 と**完全に同一**になります。

> 教訓その 2：**新しい物理は、既存の正しさを 1 mm も動かさずに足せる。** `Φ(X)=exp(−αX)`（転化が進むと鈍る“動的”減衰）と、`bio_factor`（基質そのものの“静的”ゲート）を**別の係数として分離**したことで、較正・学習・既存テストはすべて無改変のまま、実バイオマスだけが新たに表現可能になりました。

数値の手触り（稲わら, リグニン 20 %, 粒径 1 mm, CrI 0.65）：

| 前処理 | severity | `bio_factor` | 文献収率帯 |
|:---|:---:|:---:|:---|
| 単純粉砕 | 0.0 | **0.055** | 0.30–0.40 |
| 希酸 | 0.6 | 0.116 | 0.28–0.36 |
| 水熱 | 0.5 | 0.106 | 0.50–0.70 |
| 蒸気爆砕 | 1.0 | **0.157** | 0.80–1.00 |

生バイオマスの単純粉砕は攻撃速度が ~5 %、蒸気爆砕で ~3 倍に回復——「前処理が効く」が初めて数で出ます。

### 2.2 Phase 2 — 実バイオマス UI（前処理・リグニン・FPU）

#2 の最後で提案した「実験条件を一級市民に」の第一歩です。vHTS 画面に **前処理セレクタ**と**リグニン スライダー**を足し、選んだ瞬間に **Hydrolysis factor（= 阻害 × 接近度）**を表示。`run_cocktail()` がこの物性を `validator.biomass_factor()` 経由で `bio_factor` に変換し、トップヒットの糖化曲線が**実基質を反映**するようにしました。

さらに `add_literature_band()` を一般化し、**(バイオマス × 前処理) ごとの文献収率帯**を重畳。参照カクテル（酵素名・EG:BG 比・FPU/g・反応時間・出典）をキャプションで併記します。`materials.py` の `BIOMASS_DATA` にはリグニン率・粒径・結晶化度・バイオマス型・文献収率を、`PRETREATMENT_PRESETS` には severity と CSF 帯を持たせました。

### 2.3 Phase 3 — 均衡 151 酵素 ＋ AI 予測キネティクス層

ここが一番悩みました。`feature` の 141 種は **均衡が取れていて価値がある**（main は EG 偏重）。でも、その kcat/Km は OED/BRENDA 由来で、**#2 の「全文照合済みでなければ採用しない」基準を満たしません**。

そこで、**3 階層のプロビナンス**を導入しました。

```
source_type / kinetics_source
  Literature   … 全文逐語照合（#2 の 10 種）            ← 唯一の“測定値”
  AI-predicted … DLKcat による kcat 予測（配列×基質）   ← 明示ラベルの AI 値
  Estimated    … 配列ヒューリスティック（旧来の推定）    ← フォールバック
```

`populate_kinetics.py` を書き換え、酵素ユニバースを **harvested 141 種＋ LPMO 対照＋文献 10 種**に再構成。非文献酵素には DLKcat 予測 kcat（141 中 137 をカバー）を当て、`source_badge` と出典パネルに **🤖 AI-predicted** を新設しました。結果：

| 指標 | 値 |
|:---|:---|
| 総酵素数 | **151**（EG 63 / BG 54 / CBH 33 / LPMO 1） |
| プロビナンス階層 | Literature 10 / **AI-predicted 138** / Estimated 3 |
| 較正 | **α=3.80 → 72 h で 79.1 %（RE 1.2 %, PASS）= #2 と不変** |
| データ生成 | 11,325 シミュレーション |
| GP | MSE 0.045 / **R² ≈ 0.47** |
| `pytest` | **41 passed**（#2 の 31 ＋ 阻害 6 ＋ 階層 4） |

**較正が #2 と寸分違わない**のが、この設計の答えです。参照カクテルは相変わらず全文照合済みの `GUN2_THEFU / GUX1_TRIRF / BGL1_ASPNG`。AI 値や均衡データを 141 種足しても、**モデルの“原点”は検証済みの値に固定**されたままだからです。

## 3. 何を正直に捨てたか

新機能の記事ほど、捨てたものを書くべきだと思います。

- **harvested の OED/BRENDA 由来 kcat/Km は採用しなかった。** PubMed ID は付いていても #2 の全文照合を経ていないため、`Literature` には昇格させず、明示ラベルの **DLKcat（AI）**で置き換えました。「出典付き ≠ 正しい」の教訓（#2）をそのまま適用した形です。
- **CatPred（Km 予測）は同梱できなかった。** 外部ライブラリ依存で、出力 CSV も無し。よって AI-predicted 行の **Km はヒューリスティックのまま**。再現手順だけ `scripts/run_catpred_km.py` に残しました。
- **harvested に LPMO が無かった**ので、`main` の `LP9F_EMENI`（LPMO 対照）を意図的に保持。これが無いとクラス網羅テストが落ちます。
- **壊れた `libs/CatPred`・`libs/DLKcat` の submodule リンクは持ち込まなかった。**
- 配列欠落 1 件（`F4YTG7`）は ESM ゼロベクトルとして**明示フラグ**（#1 以来の fail-loud の精神）。

> 教訓その 3：**AI 予測を“測定値のフリ”をさせない。** DLKcat の値は有用だが、`Literature` と同じ棚に置けば #2 の過ちを繰り返します。階層を分け、UI のバッジで一目で区別できるようにすることが、AI を足すときの最低限の作法でした。

---

## 4. 一本化の締め — マージせず、上書きで畳む

全 Phase をコミット単位（P1 → P2 → P3）で積み、各段で `pytest` 緑・較正 PASS を確認してから、統合結果を `feature/real-biomass` に**上書き**しました。古い二股の歴史を無理にマージ commit で残すより、**「検証済みの土台＋移植した機能」という一本の事実**に畳むほうが正直だと判断したからです。これで `feature/real-biomass` は、

- **#2 の全文照合プロビナンス・較正**を土台に持ち、
- **実バイオマス物理・実機寄り UI・AI 予測キネティクス**を上乗せした、

唯一の「正しくて面白い」枝になりました。Streamlit にデプロイされる `src/analytics/app.py` も、この枝の上でそのまま動きます（新規依存ゼロ・成果物は全て追跡済み）。

---

## 5. おわりに

#2 の学びが「**出典が付いている ≠ 正しい**」だったなら、#3 の学びは「**機能が魅力的 ≠ 土台が正しい**」です。`feature/real-biomass` は面白い機能の宝庫でしたが、それらは前回暴いた誤値と旧較正の上に建っていました。畳み方は、両者を混ぜることでも、面白さを諦めることでもなく——**検証済みの土台へ、機能を一つずつ、既存の正しさを動かさずに移植する**ことでした。

`bio_factor` の中立デフォルト、較正参照の固定、3 階層プロビナンス。どれも派手さはありませんが、**「新しいものを足しても、確かめたものは壊れない」**を保証するための具体的な仕掛けです。次は #2 で設計した「予測 → 実測 → 再較正」ループに、この `bio_factor`（実バイオマス・前処理）を接続すること。自分のラボの基質で `bio_factor` を自家較正できれば、LUFFY はいよいよ「実機の隣に置ける道具」に近づきます。
