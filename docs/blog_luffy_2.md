# LUFFY 開発記 #2 — 「出典付き」の落とし穴と、実機検証へ向けたUI設計

> 前回（`docs/blog_luffy.md`）では、LUFFY を「配列 → 文献アンカー → ESM-2 埋め込み → Tellurium シミュレーション → ガウス過程(GP)による収率予測 → 逆設計」という 6 フェーズの酵素設計ループとして紹介しました。本記事はその続編です。テーマは 3 つ。
>
> 1. **前回のコードは「実は」何が問題だったのか** — モデルの問題と、その後に見つかった“もっと根深い”問題。
> 2. **今回どんな変更をして、どうなったのか** — 全文逐語照合による文献値の確定と、新規 CBH/BG 配列の ESM 特徴量再生成。
> 3. **実際に発酵実験で実機検証するために、UI をどう調整すれば使いやすくなるのか**。

---

## 0. これまでのあらすじ

LUFFY はバイオマス→エタノール変換に使うセルラーゼ（EG: エンドグルカナーゼ、CBH: セロビオヒドロラーゼ、BG: β-グルコシダーゼ）の **AI 逆設計プラットフォーム**です。100 種の実在セルラーゼ配列（UniProt, EC 3.2.1.4）を起点に、酵素の反応速度定数 kcat/Km を割り当て、温度・pH・基質を振った糖化シミュレーションで学習データを作り、GP が「この酵素・この条件なら何 % 糖化するか」を予測します。

問題は **kcat/Km をどこから持ってくるか**。ここに、本記事の核心があります。

---

## 1. 前回のコードは「実は」何が問題だったのか

### 1.1 第 1 層：モデルそのものの問題（前セッションで修正済み）

最初期の LUFFY には、シミュレーションの土台に複数のバグがありました（これらは前回の改修で対応済みです）。

| 問題 | 何がまずいか | 対応 |
|:---|:---|:---|
| 可溶性 Michaelis–Menten を**不溶性セルロースに誤用** | 結晶性セルロースには分子モル濃度が定義できず、`v=Vmax·S/(Km+S)` をそのまま当てるのは物理的に誤り | EG+CBH→セロビオース→グルコース(BG) の **3 酵素カスケード**＋アクセシビリティ減衰 `Φ(X)=exp(−αX)`＋正しい化学量論（1 セロビオース=2 グルコース）に刷新（`validator.py`） |
| 酵素クラスの**ランダム割当**・EG/BG の **id 部分一致による分割バグ** | 「β-グルコシダーゼ」が EG プールに混入するなど、生物学的に無意味な仕分け | EC 番号/注釈からの**決定論的クラス分類**（`classify_enzyme`） |
| 酵素量が画面ごとに**約 2000 倍ズレ**（Tab1/Tab3/学習で別レジーム） | 同じ酵素でも画面によって結果が桁違い | `enzyme_mM()` に**単位を一元化**（`validator.py` / `config.py`） |
| モック値・**無言フォールバック** | 失敗を隠して“それっぽい”数字を返す | **fail-loud**（`units.py`、ESM 埋め込み、DatasetManager） |

ここまでは前回ブログでも触れた話です。ところが——

### 1.2 第 2 層：「出典付き」でも間違っていた（今回発覚）

前回の改修では、kcat/Km に **DOI と測定条件を併記する文献台帳**（`data/curated/literature_kinetics.csv` ＋ `PROVENANCE.md`）を導入しました。一見すると「これで出典は完璧」に見えます。しかし、その値の `verification_status` は **`search-sourced`（検索ベース）** でした。つまり「Web 検索でそれっぽく確認した」状態で、**論文の全文（表・本文）と逐語照合してはいなかった**のです。

今回、ネットワーク許可セッションで PMC 公開全文を 1 つずつ開いて照合したところ、**“出典付き”に見えていた値が、実は出典の論文に書かれていない**という誤帰属が複数見つかりました。

| 項目 | 旧（search-sourced）の主張 | 全文照合で判明した事実 |
|:---|:---|:---|
| **BG（β-グルコシダーゼ）** | *A. niger* kcat **2589 s⁻¹** / *A. fumigatus* **4135 s⁻¹**（doi:10.1186/1754-6834-3-3） | その論文（Chauve 2010）は *A. niger* と ***T. reesei* BGL1** を比較。***A. fumigatus* は対象ですらない**。cellobiose 上の実値は **1897 / 2445 min⁻¹ ＝ 31.6 / 40.8 s⁻¹**。**min⁻¹ を s⁻¹ と読み違え**、さらに第 2 菌種を取り違えていた（約 60〜100 倍の過大） |
| **CBH（セロビオヒドロラーゼ）** | TrCel7A kcat ≈0.02 s⁻¹（**doi:10.1074/jbc.M111.269134**） | その DOI は **無関係なオートファジー論文**（Farkas et al.）を指していた。正しい一次文献は別物 |
| **EG（エンドグルカナーゼ）** | 著者「**Yang** et al.」、DOI 空欄 | 実際の著者は **Yan** et al.、DOI は **10.1002/bab.1097** |

**“実は”の核心はここです。** 「DOI が付いている」ことと「その値がその論文に書いてある」ことは**別物**でした。検索由来の値は、もっともらしい数字・もっともらしい DOI を**取り違えたまま**通ってしまう。これを防ぐ唯一の方法が、**全文（PMC 公開全文の表・本文）との逐語照合**だったわけです。

> 補足：BG の kcat が「桁違いに速い（2589 s⁻¹）」という誤値は、`config.PLAUSIBILITY_BANDS`（妥当域）まで歪めていました。妥当域が誤値に合わせて広く設定されていたため、**チェック機構そのものが誤値を追認**していたのです。

## 2. 今回どんな変更をして、どうなったのか

### 2.1 全文逐語照合のパイプライン

ネットワーク許可セッションで、各値を次の流れで**逐語確定**しました。

```
NCBI E-utilities (efetch/elink) ── 論文の同定（タイトル・著者・DOI を突合し誤帰属を検出）
        │
PMC 公開全文 / BMC・ASM・MDPI・Springer-OA ── 表/本文から kcat・Km を「そのままの数字」で抜粋（verbatim）
        │
UniProt REST ── アクセッションから配列を取得（fetch_literature_sequences.py、欠落時 fail-loud）
        │
units.py ── 報告単位（IU/mg, 1/min, mg/mL…）→ シミュレータ単位（1/s, mM）へ監査可能な換算
        │
verification_status = "full-text confirmed"（全件）＋ PROVENANCE.md に逐語引用を記録
```

ルールは明快です：**全文で確認できない値は採用しない**。確認できなかった候補酵素は（UniProt 配列が無い・有料全文で表が読めない等の理由で）不採用にしました。

### 2.2 文献酵素を 4 → 10 種に拡充（全件 full-text confirmed）

|:---|:---|:---|:---|:---|:---|

中温菌〜超好熱菌、糸状菌〜細菌、GH5/GH12/GH3/GH1 と、生物・構造の多様性も確保しました。各値の逐語引用は `data/curated/PROVENANCE.md` にあります。

> 配列について 1 点だけ正直に：商用酵素（Novozymes SP188 など）は配列が未登録のため、A. niger / A. fumigatus は**参照株オルソログ**配列を使っています。これは `PROVENANCE.md` と CSV の `notes` に明記しました。

### 2.3 新規 CBH/BG 配列の ESM 特徴量を再生成（ゼロベクトル解消）

`generate_features.py` は**配列が空の酵素に 320 次元のゼロベクトル**を割り当てる実装でした。前セッションでは CBH/BG の配列が空欄だったため、これらは事実上「特徴量なし」で GP に渡っていました。今回、配列を実取得したうえで ESM-2（`facebook/esm2_t6_8M_UR50D`）で**全 109 酵素を再埋め込み**。10 種の文献酵素すべてが**非ゼロ**ベクトルを持つこと（テーブル全体でゼロベクトル 0 件）を確認しました。

### 2.4 妥当域の再アンカー・下流の一貫再実行・較正・テスト

- **`config.PLAUSIBILITY_BANDS` を実測レンジに再設定**（誤値由来の旧 BG 帯 1e2–1e4 を修正）。チェック機構を“正しい現実”に合わせ直しました。
- **下流を一貫再実行**：`populate_kinetics` → `fetch_literature_sequences` → `generate_features` → `generate_dataset_parallel`（8,175 シミュレーション）→ `calibrate_model` → `train_yield_predictor`。
- **較正は PASS**：自由パラメータ α（アクセシビリティ係数）を文献糖化ベンチに合わせ込み、**α=3.80 → 72 h で転化率 79.1 %（目標 80 %、相対誤差 1.2 % ≤ 15 %）**。
- **`pytest` 31 passed（skip なし）**。torch 導入により、これまで skip されていた「ESM 失敗時 fail-loud」テストも通過。

### 2.5 結果の正直な評価 — GP の R² が 0.85 → 0.50 に下がった意味

GP の決定係数は旧 ~0.85 から **~0.50** に下がりました。これは**コードの劣化ではありません**。過大・誤帰属だった値を、検証済みの**現実的で広いレンジ**（EG は可溶性基質で ~6→1721 s⁻¹、CBH は結晶性セルロース上で ~0.02 s⁻¹）に置き換えた結果、予測対象である収率曲面が**より正直で難しく**なったためです。「綺麗だが嘘の R²」より「説明できる R²」を選んだ、という整理です。

## 3. 実機（発酵実験）で検証するための UI 設計

ここからが前向きな提案です。現状の UI は 3 ステージ構成です。

```
[ vHTS Screening ] → [ Inverse Design ] → [ Process Verification ]
   材料・固形分        ESM-2で変異設計        WT vs 変異体の比較
   プレートで探索       （収率±不確実性）        （Digital Twin）
```

良い点（既にある）：**Provenance & Citations パネル**（出典 DOI・報告値・測定条件）、**文献帯のオーバーレイ**（`add_literature_band`）、`source_badge`（Literature/Estimated の区別）。

しかし「シミュレーション結果を**実際の発酵実験で検証する**」用途で使うと、次のギャップが見えてきます。`app.py` を読むと、**温度・pH・反応時間がコード既定値（`config.DEFAULT_*`）に固定**されており、**エクスポート機能が無く**、**実測値を入れて予測と突き合わせる導線が無い**のです。

以下、ベンチ（実験台）と実機をつなぐための具体策を、**既存コードのどこを使えば実装できるか**まで添えて提案します。

### 3.1 「実験条件」を最初の一級市民にする（操作可能化）

現状 `run_cocktail()` は `temp=config.DEFAULT_TEMP_C, ph=config.DEFAULT_PH` を渡しています。一方、土台の `validator.run_cellulolytic_simulation()` は **temp / ph / duration を引数に取れる**ので、UI から渡すだけで実現できます。

- 追加スライダー：**温度（30–80 ℃）／pH（3–8）／反応時間（12–96 h）／酵素ローディング（5–30 mg protein/g glucan）／カクテル配合（EG:CBH:BG）**。
- 既定は「文献ベンチ条件（50 ℃ / pH 5 / 72 h / 15 mg·g⁻¹）」をプリセットとして用意（`config` の値そのまま）。
- 効果：ユーザーが**自分の発酵槽の条件**でシミュレートでき、机上の予測と実験の前提が初めて一致します。

### 3.2 予測の「不確実性」を前面に出す

GP は収率の**標準偏差**も返します（`design_engine` 側で既に取得）。スクリーニングは単一スコアだけを見せていますが、実験計画には**「予測収率 ± 95 % 信頼区間」**が要ります。

- 収率カードに `xx.x % ± y.y %`、グラフに信頼区間の帯。
- **不確実性が大きい候補ほど「まず実験で確かめる価値がある」** という能動学習的な並べ替えオプション。

### 3.3 実験プロトコルのエクスポート（`st.download_button`）

現状、設定した条件を**外に持ち出せません**（`st.download_button` がコードに存在しない）。ベンチでは「画面の数字を手写し」が事故の元です。

- **ワンクリックで実験プロトコルを CSV / Markdown 出力**：酵素 ID・**出典 DOI**・配合比・mg·g⁻¹・基質と g/L・温度・pH・時間・**予測収率 ± CI**・使用した α と較正状態。
- **プレート設計の出力**：既存の 96/384/1536 プレート（`SmartSampler.sample_plate`）を、**プレートマップ／分注ピックリスト**（液体ハンドラ取り込み用 CSV）として書き出し。
- `render_sources_panel()` の中身をそのままプロトコルに同梱すれば、**ラボノートに貼れる再現性付き手順書**になります。

### 3.4 「予測 vs 実測」比較ループ（実機検証の心臓部）

いま UI は予測を出して終わりです。実機検証には**実測を入れて突き合わせる導線**が不可欠です。

- **実測収率の入力欄**（HPLC / DNS / グルコースアッセイの結果、g/L または %）を実験行ごとに追加。
- **パリティプロット（予測 vs 実測）と残差**、誤差 %、そして較正基準（**相対誤差 ≤ 15 %**・**文献帯 50–92 % 内**）に対する**合否バッジ**を表示。判定ロジックは `config.CALIB_TOLERANCE_REL` / `LIT_RATE_BAND` を流用。
- 蓄積した実測を **`calibrate_model.py` の入力**に回し、自分のラボの基質・前処理に合わせて **α を再較正**（汎用ベンチ値からの“自家較正”）。これで「実機で測る → モデルが賢くなる → 次の設計が当たる」ループが閉じます。

### 3.5 単位の「ベンチ翻訳」電卓

モデルは mM・1/s・mg·g⁻¹ で考えますが、実験者は **酵素液の mL・力価（FPU、U/mL）・グルコース g/L・%** で考えます。

- 双方向換算ウィジェット：**mM ⇄ g/L**（`cellulose_gpl_to_glucose_equiv_mM` を表に）、**mg protein/g glucan ⇄ 必要な酵素ストック量(mL)**（`enzyme_mM` と力価入力から）、**転化率 % ⇄ グルコース g/L**。
- 「仕込み計算機」：基質 g/L と槽容量を入れると、各酵素の**実際の添加量（mL/mg）**を出力。実機の仕込みに直結します。

### 3.6 Provenance を“実験記録”に格上げ

`render_sources_panel()` は素晴らしい資産です。これを**読むだけ**で終わらせず、

- エクスポート（3.3）に DOI・報告値・assay 条件を**同梱**し、各実験が「どの論文の値に基づくか」をデータとして残す。
- `verification_status`（full-text confirmed / estimated）を実験票にも表示し、**“推定値ベースの予測”には注意ラベル**を付ける。

### 3.7 バッチ／ロット管理

- 実験 ID ごとに「条件・予測・実測・日付・担当」を保存（`DatasetManager` を拡張、または `data/experiments/*.csv` に追記）。
- 履歴ビューで**予測精度の推移**を可視化し、較正の改善を追跡。

#### まとめ：画面イメージ

```
┌─ Process Verification（拡張案）────────────────────────────┐
│  条件: [温度▣50℃][pH▣5.0][時間▣72h][ローディング▣15 mg/g]   │
│  カクテル: EG■■■ CBH■■■■■ BG■■                              │
│  予測収率: 79.1 %  ± 6.0 %   ◀ GP 不確実性                  │

```

## 4. おわりに

今回いちばんの学びは、技術ではなく姿勢の話でした。**「出典が付いている」ことは「正しい」ことを意味しない**。DOI も数字も、取り違えれば堂々と嘘をつきます。それを暴くのは地味な**全文逐語照合**であり、その作業を**再現可能なパイプライン**（E-utilities → PMC 全文 → UniProt → `units.py` → `PROVENANCE.md`）として残せたことが、本セッションの一番の成果だと思います。

次の一歩は、この「正直なシミュレータ」を**実機の発酵実験とつなぐ**こと。上の UI 改修は、すべて**既存の関数（`run_cellulolytic_simulation` の temp/ph/duration 引数、`enzyme_mM`、`calibrate_model`、`render_sources_panel`、`LIT_RATE_BAND`）の上に**載せられます。予測して終わりではなく、**測って、ズレて、較正して、また設計する**——そのループを回せる UI こそが、LUFFY を「デモ」から「道具」に変えるはずです。
